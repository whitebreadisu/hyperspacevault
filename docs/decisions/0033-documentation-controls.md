# ADR-0033: Documentation controls — gate at release, test at the enforcement surface, audit on a schedule

## Status
Proposed — 2026-10-19 (BL-271 Phase E; drafted from the owner's direction of 2026-10-18 and the Phase A evidence; awaiting owner ratification). Complements [ADR-0020](0020-three-tier-documentation-regime.md), which decided *where* documentation lives; this ADR decides *what stops it rotting*.

## Context
Every documentation audit in this project's history (BL-47 in June, the 2026-07-11 audit, BL-231 in August, BL-271 in October) was triggered the same way: the owner asked. BL-271 Phase A then measured what that trigger model had let through in the eight weeks since the previous sweep: HISTORY.md missing six releases; the Application Spec's milestone and "Last updated" banners stale; the architecture views two months behind; `/api/relay/*` absent from the Platform Spec's enforcement-surface lists after a feature PR that touched no spec; `database.py` line citations drifted by twelve lines; phantom CI job names; hand-counted numbers wrong by one; an ADR shown as Proposed in the spec and Accepted on disk; a resolved backlog item still active and an archived one with no tombstone.

One Tier-1 artefact never drifted in that period: the release-notes entry, which `promote-prod.yml` has refused to ship without since BL-210. It is the only documentation claim with a mechanical gate at the event that would otherwise stale it. The ritual rules in CLAUDE.md (same-PR supersession, the drift grep sweep, ✅-flip = archive) held for everything a session does *inside a PR*; they failed for everything tied to a *release event* (banners, HISTORY, the views) or to *code that changed without a spec PR* (the relay routes). The owner's framing on 2026-10-18: the knowledge layer is part of the harness, and a harness whose only audit trigger is the owner is missing its controls.

## Decision
Documentation currency is enforced by three mechanical controls, each placed where the corresponding drift class enters, and recorded in one table — the Documentation Controls Register, `SWU_Platform_Spec.md` §2.8 — so the controls are themselves Tier-1 and auditable:

1. **Gate at release.** The prod promote (`promote-prod.yml`) refuses a commit unless, at the promoted SHA: HISTORY.md's generated Releases table carries the version being shipped; the specs' "Last updated" banners are current with their files' history; each architecture view is "as of" the release's major.minor; the Application Spec's milestone banner names the version; and the generated section index is fresh. The gate runs main's copy of the check scripts against the promoted tree (like the CI gate), judges only release-event checks (never content rules, so a rollback to an older tree is not refused for today's content standards), and is waived by the same `allow_stale_notes` input that waives the notes date for rollbacks. The CI gate also requires the image build, so a docs-only SHA is refused with a message rather than at `terraform apply`.
2. **Test at the enforcement surface.** Where a spec makes a claim about code behaviour that a program can introspect, a test compares the two and fails CI on any difference: the route registry (`backend/app/tests/test_route_registry.py` ↔ Platform Spec §1.3, BL-271 Phase B2), the phone event registry (`frontend/src/mobile/docs.test.ts` ↔ Application Spec §22/§25, BL-190), and the generated artefacts' freshness (`docs_index.mjs --check`, `history-releases`). The two machine-checked specs classify as code in CI so their tests run on spec-only changes.
3. **Audit on a schedule.** `docs-audit.yml` runs monthly (and on demand): every documentation check at its strictest, both generated artefacts, the route-registry test, and the report "spec sections whose cited code changed after the section's dated banner" (the section index records what each section cites; `git log` says when it last changed). The report is written into one rolling GitHub issue — created once, edited and commented on every run, red while findings remain — which the owner triages with a fixed vocabulary: **drift** (the spec is behind the code → doc fix), **defect** (the code is behind the spec → BL item), **intentional-unbuilt** (design-stage text → the private design shelf, ADR-0020 amendment). That issue replaces the owner's request as the audit trigger.

Two supporting rules: **generate, don't maintain** — wherever the source of truth is already machine-readable (release notes, spec headings, cited paths) the Tier-1 artefact is rendered from it and a freshness check replaces hand upkeep (HISTORY's Releases table, `INDEX.md`); and **a drift class found by an audit gets a control, not a rule** — the fix for a recurrence is a check in the register, and a CLAUDE.md sentence is written only when no mechanical form exists.

## Rationale
- The evidence is one-sided: the gated artefact held, every ungated one drifted. Gating at the release event is the cheapest place because the event is already machine-controlled and already serialised (one promote at a time).
- Testing at the enforcement surface is the only control that would have caught the single most important Phase A finding (unregistered relay routes), because that drift entered through a PR that no documentation rule could see.
- A scheduled audit converts "the owner remembers to ask" into "the harness reports", at the cost of one short issue a month. Its output must be a durable, editable surface (an issue), not a log, so triage decisions accumulate.
- Alternatives considered: a per-PR "docs touched?" checklist (declined: it is a rule, and rules are what failed); blocking every PR on an exhaustive content audit (declined: too slow, and the findings are mostly release-tied, not PR-tied); generating the whole spec from code (declined: the specs carry intent and decisions that code cannot express — "code is behaviour, spec is intent, ADR is constraint").
- Gate checks are deliberately coarse on patch releases: a view banner compares at major.minor, so a hotfix is never held for an architecture redraw; the minor release is the review trigger.

## Consequences
- + After BL-271, no drift class found by Phase A can recur without a mechanical signal (a refused promote, a red PR, or an audit finding) before the next owner audit — the standard Objective 2 of the assessment set.
- + The release ritual gains four concrete to-dos per minor release, all mechanically checked: finalise the notes date, regenerate HISTORY, update the App Spec milestone banner and the three view banners, regenerate the index. The first live run is the v2.1 promote.
- + BL-13 (an owner-performed manual review) is retired; the audit issue is its standing replacement.
- − Every spec edit now carries a regeneration step (`docs_index.mjs --write`); the index diff is machine churn and not for human review.
- − A promote can be refused for a documentation reason. That is the point; the waiver covers rollbacks, and a genuine emergency can use it deliberately with the reason in the dispatch.
- − Branch protection is not "strict", so two clean-merging PRs can leave a generated file stale on main until the next run reddens; the audit catches what the PR job misses.
- Register: `SWU_Platform_Spec.md` §2.8 lists every control with its drift class, location and level; CLAUDE.md's Documentation Drift rule points there.
